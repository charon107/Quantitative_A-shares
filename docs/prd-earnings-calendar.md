# PRD：财报日历（每日财报更新追踪）

| 字段 | 内容 |
|------|------|
| 版本 | v1.0（草案） |
| 日期 | 2026-07-24 |
| 状态 | 待评审 |

---

## 1. 背景与问题

财报季（年报/一季报 1–4 月、半年报 7–8 月、三季报 10 月）是基本面信息密度最高的窗口期。当前看板的财务数据（`stock_fundamental` / `stock_fundamental_quarterly` / `stock_forecast` / `stock_express`）由 `fundamentals_refresh.yml` 驱动，**一年只在 5/9/11 月各跑一次全量刷新**。这意味着在财报披露最密集的月份里，用户无法及时知道"今天哪些公司发了财报"，只能等季末统一刷新后再回看——信息时效性完全缺失。

用户原话："在公司集中发布财报的时间段内，每日查一下各个股票有没有更新财报，选定日期后还可以查询当天更新的财报。"核心诉求是**财报季内的每日时效性 + 按公告日回看**。

一个关键事实：上述四张表**已经带 `ann_date` 公告日字段**，查询侧只需按日期过滤，几乎零新成本。真正的工程缺口在入库节奏（见 §6）。

## 2. 目标与非目标

### 2.1 目标

- 财报季内，系统**每日自动增量抓取**当天新披露的财报（正式财报 + 业绩预告 + 业绩快报），入库延迟 ≤1 个自然日。
- 提供一个「财报日历」页面：用户选定任意日期，1 次点击内看到当天所有披露财报的公司及核心数据。
- 用户可以按"正式财报 / 业绩预告 / 业绩快报"过滤，可以快速定位到自己收藏股的披露。
- 非财报季页面可用（展示历史数据），不做禁用。

### 2.2 非目标（本期不做）

- 财报 PDF 原文抓取、全文展示或跳转交易所公告页。
- 披露前的"预计披露日期"日历（预约披露表 tushare 无稳定免费源）。
- 财报更新的推送/提醒（订阅、邮件、Webhook）。
- 财务报表三大表逐项明细展示（个股页已有季度基本面图，本期列表只给摘要指标）。
- 覆盖范围扩展（科创板/创业板/北交所），仍限现有沪深主板口径。

## 4. 入口方案

复用现有信息架构，无争议项：**顶部导航新增「财报日历」tab**，位置建议放在「个股查询」之后、「排行榜」之前（与收藏页模式一致，见 `docs/prd-stock-favorites.md` §4 方案 A 的决策理由，此处不再重复评估）。

## 5. 功能需求详述

### 5.1 财报日历页（P0）

- **页面结构**（自上而下）：
  1. **日期选择区**：月历组件，有披露的日期上显示角标（当日披露家数）；今日高亮；默认选中"最近一个有披露的日期"（不一定是今天，周末/节假日无披露）。
  2. **类型过滤条**：全部 / 正式财报 / 业绩预告 / 业绩快报（chips 多选或单选，默认"全部"）。
  3. **收藏过滤开关**：「只看收藏」toggle（P1，复用 `favorites.ts`）。
  4. **结果列表**：选中日期 + 过滤条件下的披露记录，按报告期排序（同报告期按代码）。
- **列表行内容**（复用 `HotStocks.tsx` 的行排版语言）：
  - 股票名称 + 代码 + 收藏星标（可就地收藏/取消）
  - 类型标签（带颜色区分：正式财报 / 预告 / 快报）
  - 报告期（如 `2026-06-30 · 半年报`）
  - 核心指标摘要：
    - 正式财报：单季或累计营收、归母净利润及同比（取 `stock_fundamental_quarterly` 的 `q_revenue`/`q_net_profit`/`q_netprofit_yoy`）
    - 业绩快报：营收、净利润、`yoy_sales`/`yoy_dedu_np`
    - 业绩预告：类型（预增/预减/扭亏/首亏…）+ 变动幅度区间（`p_change_min`~`p_change_max`）
  - 同一公司同一天既有快报又有正式财报时**合并为一行**，类型标签并列展示，不重复占位。
- **点击行为**：点击行 → 复用 `openStock(code)` 跳转个股查询页，提供"返回财报日历"。
- **状态处理**：
  - 空态：选中日期无披露 → "当日无财报披露"，并提示最近一个有披露的日期（可点击跳转）。
  - 加载/失败态：复用 `Loading` / `ErrorState`。
- **非财报季**：页面照常可用，默认日期落在最近一次披露日，无需特殊文案。

### 5.2 每日增量入库（P0，本需求的核心工程项）

- **触发**：`fundamentals_refresh.yml` 增加财报季每日 schedule，cron 建议北京 **19:30**（A 股公告集中在 15:00 收盘后至晚间，tushare 通常当晚入库；19:30 抓当天 `ann_date` 可覆盖绝大多数；次日 07:30 再补跑一次兜底晚间漏抓）：
  - 窗口一：`1月1日 – 4月30日`（年报 + 一季报）
  - 窗口二：`7月1日 – 8月31日`（半年报）
  - 窗口三：`10月1日 – 10月31日`（三季报）
  - 窗口外每日任务直接跳过（workflow 内判断日期，秒退，不占 runner）。
- **增量逻辑**（已按代理实际能力实测调整，2026-07-24）：
  1. **业绩预告**：`forecast` 支持 `ann_date` 按日全市场查询，单次直取当日名单与数据（1 次调用）。
  2. **正式财报**：代理**不支持** `income`/`fina_indicator` 的 `ann_date` 按日查询（返回空）。改走 `disclosure_date`（披露计划表）分页全量拉取（limit/offset，约 50 页 ≈ 3.5 分钟），按 `actual_date` 实际披露日过滤当日名单（含 2 天回溯尾，吸收"披露日与代理报表入库的时间差"防漏抓）；名单内股票逐只补四张报表 raw（每股 7 次调用，与全量一致），峰值日含回溯尾约 750 只 ≈ 60 分钟。
  3. **业绩快报**：代理仅支持逐股查询。快报非强制披露、集中在 1–2 月（年度）与 7–8 月（半年报），只在这两个窗口做全主板逐股扫描（约 3200 次调用 ≈ 36 分钟），3–4 月/10 月窗口不扫（快报稀少，正式财报股票的逐只补抓会顺带带上）。
  4. 复用现有 `fetch → parquet → scp → load` 管道（bundle 推送模式不变），`load_fundamentals.py --incremental` 只做 upsert，跳过逐年选股与退市清理（选股仍由 5/9/11 月全量任务负责）。
- **tushare 数据时效兜底**：tushare 的 `ann_date` 偶尔滞后实际公告 1 天；补跑机制（见上）天然吸收，无需额外处理。

### 5.3 后端 API（P0，2 个新端点）

| 端点 | 说明 |
|---|---|
| `GET /api/earnings-calendar/dates?month=2026-08` | 某月各日期的披露家数（日历角标用），返回 `[{date, count}]`；不传 month 时返回最近一个有披露的日期 |
| `GET /api/earnings-calendar?date=2026-08-27` | 当日披露列表，行内聚合三张表（正式财报/快报/预告），按 §5.1 的结构返回 |

- 实现：DuckDB 按 `ann_date` 过滤三表 + `stock_meta` join 取名称，直连不走 Redis（与个股财务接口一致，见 `src/api/routes/stocks.py:54-55` 的既有决策）。
- 收藏过滤由前端做（收藏在 localStorage，后端无感知）。

### 5.4 前端增强（P1）

- 「个股查询」页的名称区域，若该股**近 7 天内有新披露**，在名称旁显示"新财报"小徽标，点击滚到基本面图。（依赖 5.3 的日历接口按 code 过滤，或给个股接口加 `latest_ann_date` 字段，实现时任选低成本方案。）

## 6. 方案对比与推荐

**数据源约束**：全部数据只取自 tushare（既定决策，不引入 baostock/akshare 等其他源）。本需求的查询与增量抓取均基于 tushare 的公告日字段。

### 入库节奏方案

| 方案 | 做法 | 结论 |
|---|---|---|
| **A：财报季每日增量（✅ 推荐）** | 按 `ann_date` 取当日名单，只补名单内股票 | 日增 ≈10 分钟内，限频无压力；时效 T+0 |
| B：财报季每日全量 | 现有全量脚本改每日跑 | 每次 4 小时、3200 只 × 7 调用，限频与 runner 成本都不可接受，排除 |
| C：不动入库，只查历史 | 页面只展示已有 `ann_date` 数据 | 数据一年只更新 3 次，"每日查更新"形同虚设，不满足需求，排除 |

### 为什么可以相信 `ann_date` 口径

四张表的 `ann_date` 均来自 tushare 官方公告日字段，与交易所披露日一致（滞后 ≤1 天的边缘情形由补跑吸收）。业绩预告同一报告期多次修正均保留（主键含 `ann_date`），日历上会自然出现"修正公告"记录，符合真实披露语义，无需去重。

## 7. 边界与异常

| 场景 | 处理 |
|------|------|
| 当天无披露（周末/节假日/窗口外） | 列表空态 + 引导跳到最近披露日 |
| 某日披露量极大（4/30、8/31 法定截止日，可能上千家） | 列表虚拟滚动或分页（每页 100）；日历角标只显示数字不受影响 |
| 增量任务当天失败（tushare 代理抖动） | workflow 失败告警；次日补跑自动覆盖（补跑按 `ann_date` 取的是"昨天的"，漏不掉） |
| tushare `ann_date` 与真实披露日偏差 | 接受 ≤1 天误差，页面文案用"公告日"而非"披露日" |
| 快报/预告早于正式财报多天出现 | 正常：它们会出现在各自的 `ann_date` 上，日历忠实反映时间线 |
| 退市股/停牌股当日披露 | 照常展示，点击跳转个股页走既有 404/空态逻辑 |

## 8. 验收标准

1. 财报季窗口内，工作日早晨打开「财报日历」，默认日期能看到前一交易日披露的完整列表（快报/预告/正式财报类型标签正确）。
2. 切换到任意历史日期（含非财报季），列表数据与库内 `ann_date` 一致；无披露日期展示空态。
3. 4/30 类高峰日列表不卡死（分页/虚拟滚动生效）。
4. 「只看收藏」开关只过滤显示，不影响接口；在列表行可就地收藏/取消。
5. 点击任意行跳转个股查询页，该股季度基本面图包含该次新报告期数据。
6. 增量 workflow 在窗口外日期自动跳过（秒退）；窗口内单日增量耗时 <30 分钟。
7. 现有 5/9/11 月全量刷新 + 逐年选股链路不受增量模式影响，照常运行。

## 10. 开放问题

1. **每日两次抓取（19:30 + 次日 07:30 补跑）是否必要？** 若接受 T+1 完整时效，可简化为每日早 07:30 抓前一自然日一次，workflow 更简单。倾向先单次 19:30 上线，观察漏抓率再决定。
2. **日历组件选型**：自研月历（全月格子 + 角标，约 100 行）vs 仅"日期下拉 + 前后日翻页"。若 v1.0 想控制范围，可先上翻页式，月历角标放 v1.1。
3. **正式财报列表的指标口径**：单季（`q_` 前缀）还是累计？倾向单季营收/净利润 + 同比，与个股页季度图口径一致。
